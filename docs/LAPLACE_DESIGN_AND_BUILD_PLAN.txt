1. VISION AND ONE-LINE PITCH
==============================================================================

THE PROBLEM
People and machines constantly have to remove one piece from a pile without
bringing the rest down: rescuers moving debris off a trapped person, warehouse
robots pulling boxes from a stack, demolition and repair crews taking out a
part. Today that decision is human gut feel under pressure. When it is wrong,
structures collapse.

THE INSIGHT
AI can now SEE objects. It cannot yet FORESEE consequences. Before a person
or a robot acts on a physical structure, it should be able to rehearse the
action in a digital copy, know what it cannot see, ask for exactly the missing
view, and commit to a prediction before anyone touches anything.

WHAT LAPLACE IS (prototype)
A wearable + AI system that:
  1. Builds a live 3D twin of a physical structure from camera views
     (phone on tripod and Meta AI glasses).
  2. Tracks what it has seen, what it has confirmed, and what is hidden.
  3. Takes a spoken question: "What happens if I pull this block?"
  4. Asks for the one view it needs when a hidden part would change the
     answer ("I can't see behind level 9. Show me the left side.").
  5. Gives a model assessment - PREDICTS STAND / PREDICTS FALL /
     INCONCLUSIVE - locks the prediction with a
     timestamp and fingerprint, and speaks it into the operator's ear.
  6. Compares the prediction with what reality does, on camera, unedited.
  7. Plans a safe multi-step extraction ("reach the survivor in 3 moves").

The test structure is a block tower: small, safe, and - critically -
FALSIFIABLE. It is our crash-test dummy for "a stack you must take apart".

ONE-LINE PITCH (use verbatim)
  "Robots and AI can see objects. They can't yet foresee consequences.
   LAPLACE predicts what happens before anyone touches anything, asks when
   it's unsure, and proves itself against reality."

CLOSING LINE
  "Today, a test tower. Tomorrow, rescue teams, warehouse robots, demolition
   crews. Rehearse the move before you make it."

NAME
"LAPLACE" refers to Laplace's demon: an intellect that, knowing the present
state and the laws, computes the future. Working name; see Section 14.

LOCKED
D1  Concept: block tower physical-foresight demo. Rejected: pendulum/ball
    "LAPLACE physics discovery", box stacks (felt weaker), pivoting again.
D2  Framing: "physical foresight for people and machines"; rescue scene opens
    the video for emotion; warehouses/robots named as nearest real use.
D3  Tower is modelled as a discrete GRID: ~18 levels x 3 slots, per-level
    orientation DETECTED (not assumed to alternate).
D4  The scene model is built by SAM 3.1 + our code, NOT by the reasoning model
    reading raw photos (Muse Wonder took 217 s on a raw photo; Section 9).
D5  Predictions come from a MODEL ASSESSMENT (static stability check in
    code) under stated assumptions. It is not "the truth": the physical
    trial is the outcome. Three separate things, always labelled:
      Model assessment : PREDICTS STAND / PREDICTS FALL / INCONCLUSIVE
      Physical outcome : OBSERVED STAND / OBSERVED FALL / UNCLEAR
      Comparison       : MATCH / MISMATCH
    Physics-engine animation, if used, is labelled "illustration".
D6  The AI asks for a view ONLY when the hidden part would change the
    prediction (value-of-information rule, computed in code; Muse phrases
    and explains it).
D7  Muse Wonder = planning/judgement over structured scene text.
    Muse Spark 1.3 = fast conversational turns.
D8  Capture: S25 on tripod is the primary camera; Meta glasses provide the
    operator's views (requested side views first, walk-around last).
D9  Glasses audio route: in-stream camera audio, 16 kHz PCM (beta, available
    in Developer Mode). Fallback: HFP headset mode (8 kHz).
D10 Voice back: the laptop generates ONE audio clip per reply; it plays to
    the glasses (via phone) AND on the laptop (OBS / audience). Captions
    always on screen.
D11 Display: split / three-panel laptop UI. No projector. No wearable
    display (Adventurer glasses have none).
D12 SAM 3D (via fal.ai hosting Meta's open model) is used for visuals only:
    the opening "photo becomes 3D" moment and the "beyond blocks" finale.
D13 No Neural Band purchase. Glasses capture button = optional "confirm".
D14 Head-on views only for slot checks. Angled glasses frames are ignored.
D15 (v1.1) A slot stays UNKNOWN unless an image or an operator confirmation
    supports its state. A missed detection is not proof of absence; a dark
    patch is evidence to investigate, not proof of a gap.
D16 (v1.1) Physical outcome is OPERATOR-CONFIRMED in v1 (video retained,
    labelled). Automatic outcome detection is later work and must return
    UNCLEAR when it cannot decide.
D17 (v1.1) Calibration trials tune thresholds; thresholds are then FROZEN;
    a separate set of new evaluation trials is what we report.
D18 (v1.1) The core video rests on: one computed PREDICTS STAND that stands,
    one computed PREDICTS FALL that falls, one meaningful missing-view
    request, and the evidence. The survivor planner appears only if it
    passes its reliability gate (Section 10).
D19 (v1.1) The 360-degree glasses walk-around stays in the plan as the
    final stretch milestone (C1), with the field-operator experiment
    after it (C5). Only free-form mesh reconstruction is cut.

CUT (and why)
  - Free-form 3D MESH reconstruction as the physical model: the block grid
    is more reliable and checkable. (The 360-degree walk-around that fills
    the grid is NOT cut - it is stretch milestone C1; see D19.)
  - Quest / mixed reality: new platform, too risky for one person.
  - Projector overlay: split screen gives the same credibility.
  - Mass/material from SAM 3D: physically unjustified.

6. CORE METHODS
==============================================================================

6.1 TOWER GEOMETRY
  Standard block: 1.5 cm high x 2.5 cm wide x 7.5 cm long (MEASURE ours on
  Day 1 with a ruler; store in config). A level = 3 blocks side by side,
  7.5 x 7.5 cm footprint, 1.5 cm high. Full tower = 18 levels, 54 blocks.
  Axes: x = left-right in the FRONT view, y = front-back, z = up.
  Level orientation:
    ENDS  : long axes along y. Front view shows 3 end faces.
            Slots indexed by x: L, M, R.
    SIDE  : long axes along x. Front view shows the long face of the front
            block only. Slots indexed by y: F, M, B.
  The side view (plate turned 90 degrees) swaps the two: SIDE levels show
  their ends there. For a neat, aligned tower, front + side views CAN
  resolve every slot; occlusion, recessed blocks, perspective and missed
  detections can still leave slots UNKNOWN (D15). Back/opposite views and
  operator confirmation close the remaining gaps.

6.2 SLOT STATES AND PROVENANCE
  Each slot has state + source:
    PRESENT_OBSERVED   seen directly (SAM box + image check), with view id
    EMPTY_OBSERVED     gap seen directly
    PRESENT_CONFIRMED  operator confirmed (click / voice)
    EMPTY_CONFIRMED    operator confirmed
    INFERRED           derived by rule (e.g., recessed block seen through gap)
    UNKNOWN            not yet determined
  Every change creates a new scene version. Nothing is overwritten silently.

6.3 FROM PHOTO TO SLOTS (slot check)
  Step 1  SAM 3.1 on the head-on photo, prompt "wooden block" -> boxes.
  Step 2  Tower bounds = union of boxes, refined by the widest bottom rows.
  Step 3  Row clustering: group boxes by vertical centre into levels;
          level height = tower height / level count (count from rows,
          sanity-checked against measured block height).
  Step 4  Per level, orientation from box aspect ratio:
          end face ~ 2.5:1.5 (~1.7); long face ~ 7.5:1.5 (~5).
  Step 5  ENDS levels: map each end box to slot L/M/R by its x position
          relative to tower bounds. A detected box -> PRESENT_OBSERVED.
          No box -> the slot is UNKNOWN by default (a miss is not proof of
          absence). It becomes EMPTY_OBSERVED only with positive evidence:
          the background (wall colour) or a recessed block face is visible
          through the gap AND a re-check (SAM on a close crop of that
          level) also finds no block. Otherwise it stays UNKNOWN, and the
          ask-for-view / operator-confirm flow resolves it.
  Step 6  SIDE levels (front view): long face present -> F = PRESENT;
          M and B = UNKNOWN. Long face absent and recessed wood visible ->
          F = EMPTY, M/B = UNKNOWN. Resolved later by the side view.
  Step 7  Glasses frames: only head-on, sharp frames (marker angle < ~20
          degrees, Laplacian sharpness above threshold); for weak frames,
          run SAM on per-level crops to improve recall.
  Evidence so far: clean tower, phone head-on, SAM found 35/36 visible
  faces per view. That is face detection, NOT yet proof of correct
  54-slot reconstruction on altered towers - measured in 12.3a.

6.4 STABILITY CHECK (model assessment; D5)
  Model: rigid blocks, gravity, no adhesion. For each interface between
  level i and level i+1 (bottom to top), after the proposed removal:
    support polygon = convex hull of all contact rectangles between
                      remaining blocks of level i and level i+1
                      (block footprints intersect -> contact rectangle)
    load COM       = centre of mass of every block above the interface
                      (equal masses unless measured otherwise)
    margin         = signed distance from load COM (projected on xy) to
                      the hull boundary; positive = inside
  Second check (v1.1) - per-block local support: for every block, the
  centre of mass of that block plus everything resting on it (directly or
  through blocks above) must lie inside the hull of ITS OWN contacts with
  the level below. This catches a block that loses support locally even
  when the layer-level check passes (mainly matters for misaligned or
  offset blocks).
  Assessment = worst (minimum) margin over both checks:
    margin >= +M_SAFE              -> PREDICTS STAND
    margin <= -M_FALL              -> PREDICTS FALL (report the critical
                                      interface or block)
    otherwise                      -> INCONCLUSIVE
  Thresholds: M_SAFE = 4 mm, M_FALL = 1 mm are STARTING PARAMETERS ONLY,
  not confidence limits. They are tuned on calibration trials and then
  frozen before evaluation trials (D17).
  Also report the critical interface ("level 9 now rests only on its left
  block") - this is what the agent explains.
  Sanity cases (unit tests; idealised, perfectly aligned 7.5 cm level).
  Verified numerically on Oct 28 with this method:
    - Full tower / middle block removed : margin +37.5 mm -> PREDICTS STAND
    - One side block removed            : +12.5 mm        -> PREDICTS STAND
    - Both side blocks removed          : +12.5 mm        -> PREDICTS STAND
    - Middle + one side removed         : -12.5 mm        -> PREDICTS FALL
  These hold for an aligned tower. Real outcomes also depend on block
  offsets, height differences and how the blocks above are supported - so
  physical trials, not these cases, decide whether the model is useful.
  Known limits (state honestly): real blocks differ in height (some carry
  no load), pulling adds friction and contact forces, the upper stack is
  not perfectly rigid, contact mechanics are richer than a support-polygon
  test. INCONCLUSIVE exists for exactly these reasons.
  Upgrade path if trials show systematic misses: measure per-level offsets
  from the photos and use real block positions instead of ideal slots.
  Removal protocol for trials: one finger, slow straight push along the
  block's long axis; tower settles 3 s before outcome is read.

6.5 ASK ONLY WHEN IT MATTERS (value of information; D6)
  Given a proposed removal and the set U of UNKNOWN slots:
    1. Evaluate the verdict for the plausible fills of U (each unknown
       present/empty; cap combinations, prioritise slots at or above the
       removal level and in the critical interfaces).
    2. If all fills give the same verdict -> answer, noting the assumption.
    3. If verdicts differ -> pick the unknown slot whose resolution splits
       the outcomes most; map it to the view that reveals it (SIDE levels
       -> side view; back slots -> back view) -> ASK for that view.
    4. If the operator cannot provide it -> answer INCONCLUSIVE and
       say why.
  Muse phrases the request and the explanation. Code makes the decision.

6.6 PREDICTION LOCK
  Before any physical action the system writes a record:
    {scene_version, scene_hash, action, assumptions, verdict, margins,
     critical_interface, model_versions, timestamp_utc}
  SHA-256 over the canonical JSON = fingerprint. UI shows "PREDICTION
  LOCKED 23:41:07  #a3f9c2". Records are append-only (predictions.jsonl).
  Corrections create new records that reference the old one.
  What the fingerprint does and does not prove (v1.1): it shows a saved
  record was not changed afterwards. On its own it does NOT prove the
  record existed before the removal - a hash and a local timestamp could
  be generated later. Timing is proven by:
    1. a continuous, unedited recording with the locked prediction on
       screen before the action,
    2. the retained event log and raw source video, and
    3. the repo and trial records showing how the prediction was made.
  Optional (COULD, C6): independent timestamp - push each lock record to
  the GitHub repo (server-side commit time) or an RFC 3161 timestamp
  service before the removal. Never describe the hash as tamper-proof.

6.7 PHYSICAL OUTCOME (D16)
  v1: OPERATOR-CONFIRMED. After the removal and a 3 s settle, the operator
  records OBSERVED STAND / OBSERVED FALL / UNCLEAR (button or voice). The
  before/after frames and the full video are retained and linked. The UI
  labels the source "operator-confirmed, video retained".
  Later (optional): automatic assessment from before/after frames using
  SAM 3.1. A shrinking box is NOT a reliable collapse definition on its
  own (partial collapse, lean, camera bump, a hand in view), so the
  automatic check must return UNCLEAR whenever it is not decisive, and it
  never overrides the operator.
  Outcome record links to the prediction fingerprint and stores the
  comparison: MATCH / MISMATCH / NOT COMPARABLE (inconclusive or unclear).

6.8 EVIDENCE MAP AND EXTRACTION PLANNING
  Evidence map (v1.1, replaces "danger map"): for every present block, run
  6.4 together with 6.5 and show one of three states on hover and as a
  colour + pattern + icon (colour is never the only cue):
    "Model predicts stands"
    "Model predicts fall"
    "Need more information" -> a glowing line points to the side of the
       tower whose view would resolve it (from 6.5). As the operator walks
       round with the glasses, the missing region fills in and every
       affected block's state updates live.
  This is the signature interaction: the AI directs the human to gather
  exactly the evidence that resolves its uncertainty.
  Extraction planning (SHOULD, gated): goal = set of blocks to clear (e.g.,
  those caging the "survivor"). Beam search over removal sequences (depth
  <= 3), each step must PREDICT STAND with margin; score = minimum margin
  along the path. The scene is re-checked from fresh photos after every
  physical step (errors accumulate otherwise). Muse Wonder explains the
  plan and narrates guidance.
  Reliability gate: the planner appears in the video only if 4 of 5 full
  rehearsal runs complete with every step matching reality.

6.9 LIVE TWIN (UI)
  three.js scene of 54 slot boxes. Visual states:
    UNKNOWN = translucent ghost; OBSERVED = solid wood; CONFIRMED = solid
    + tick badge; INFERRED = hatched; selected = outline glow;
    predicted motion = luminous trails (labelled simulation).
  Each slot animates ghost -> solid when its state changes: this is the
  "tower builds itself" effect and it is truthful by construction.

6.10 GLASSES CAPTURE STAGES
  Stage A  Tripod front + side photos -> full twin.          (MUST)
  Stage B  Agent requests a side; operator looks; glasses photo fills the
           missing slots.                                       (SHOULD)
  Stage C  360-degree walk-around: ArUco marker per plate side gives face
           id + angle; auto-capture head-on frames; the twin fills in
           progressively and clearly marks observed vs not-yet-observed
           regions. Final stretch milestone; preserves the original
           vision.                                              (COULD, C1)
  Stage D  Field-operator experiment: the same "I can't see X - show me
           that side" interaction on a simple non-hazardous assembly
           (e.g., a bracket with a hidden fastener).            (COULD, C5)
  Separate, optional: SAM 3D produces an ESTIMATED visual reconstruction,

6.11 VOICE LOOP
  In : glasses audio (PCM16, 16 kHz) -> laptop -> Muse Voice Transcribe
       realtime WebSocket (server VAD) -> transcript events.
  Out: agent reply text -> TTS clip (laptop) -> phone (plays to glasses)
       + laptop speakers/OBS + caption. One clip, two destinations.

7. DATA MODEL AND MODULE CONTRACTS
==============================================================================

7.1 CORE TYPES (Python dataclasses; JSON-serialisable)
  Slot     {level:int, index:int (0..2), orientation:"ENDS"|"SIDE",
            state:SlotState, source:{kind, view_id, detail}, updated_at}
  Scene    {version:int, levels:[Level], block_dims_mm, created_from:[view
            ids], hash}
  View     {view_id, device:"phone"|"glasses", face:"front"|"left"|...,
            image_path, sam_raw_path, angle_deg?, sharpness?}
  Action   {type:"remove", level, index, method:"push_long_axis"}
  Verdict  {result:"PREDICTS_STAND"|"PREDICTS_FALL"|"INCONCLUSIVE"
            |"NEEDS_VIEW", min_margin_mm,
            critical_interface, per_interface:[...], assumptions:[...]}
  Lock     {fingerprint, scene_hash, action, verdict, ts_utc, ...}
  Outcome  {fingerprint, observed:"OBSERVED_FALL"|"OBSERVED_STAND"|
            "UNCLEAR", source:"OPERATOR"|"AUTO", comparison:"MATCH"|
            "MISMATCH"|"NOT_COMPARABLE", evidence_paths, ts_utc}

7.2 KEY FUNCTIONS (contracts; pure where possible)
  sam.segment_image(path, prompt) -> SamResult{boxes, masks?, raw_path,
                                                latency_s}
  scene.locate.find_levels(boxes, image) -> [RowBand]
  scene.slots.classify(view, row_bands, boxes, image) -> [SlotObservation]
  scene.merge.apply(scene, observations) -> Scene (new version)
  physics.stability.evaluate(scene, action, params) -> Verdict
  physics.planner.evidence_map(scene) -> {(level,index): Verdict|AskView}
  physics.planner.plan(scene, goal, depth) -> [Action]
  physics.voi.decide(scene, action) -> Answer | AskView{slot, face, reason}
  evidence.ledger.lock(scene, action, verdict) -> Lock
  evidence.outcome.record(fingerprint, observed, source, media) -> Outcome
  evidence.outcome.auto_assess(before_img, after_img) -> suggestion or
                                                       UNCLEAR (later)
  agent.policy.handle_utterance(text, context) -> Reply{text, ui_events}
  tts.speak(text) -> AudioClip{wav_path, duration_s}

7.3 PHONE <-> LAPTOP PROTOCOL (WebSocket JSON envelope)
  {type, seq, ts_ms, payload}
  phone -> laptop: hello, frame{jpeg_b64, w, h, source}, photo{...},
                   audio{pcm16_b64, rate:16000}, button{kind}, status
  laptop -> phone: capture_photo{source}, play_audio{wav_b64}, set_stream
                   {quality, fps}, ping
  Frames at 1-2 fps are enough. Photos on demand at full resolution.

11. ENGINEERING PRINCIPLES
==============================================================================
These are binding for every contributor and every coding agent.

11.1 MODULAR BY DEFAULT
  - One responsibility per module (Section 5.4). Perception does not know
    about the UI; physics does not call APIs; the agent does not compute
    physics, it calls the physics tool.
  - Pure functions for all logic that can be pure (geometry, stability,
    slot classification, VOI, planning). Side effects (network, files,
    devices) live at the edges in clients/ and server/.
  - Interfaces are typed (dataclasses + type hints). Module contracts in
    Section 7 are the API; change them deliberately and update this doc.

11.2 STEP BY STEP
  - Build the thinnest end-to-end slice first, then deepen.
  - Every step has a DONE-WHEN check that can be demonstrated in under a
    minute (a test passing, a CLI output, a screenshot).
  - One change at a time; run tests; commit with a clear message. Never
    stack three untested changes.
  - If a step takes more than 2x its estimate, stop, write down why, and
    pick the fallback from Section 13.

11.3 DEBUG STATEMENTS AND OBSERVABILITY
  - Python logging everywhere; no bare print in library code.
  - Levels: DEBUG (internals), INFO (milestones), WARNING (degraded but
    continuing), ERROR (failed operation). LAPLACE_LOG_LEVEL in .env.
  - Log at every boundary: each API request/response (model, latency,
    tokens, estimated cost, request id), each scene version change, each
    verdict with margins, each WebSocket message type, each device state
    change on the phone (Android Logcat tag "LAPLACE").
  - Every session writes a run folder: runs/<timestamp>/ with inputs,
    raw API outputs, scene versions, predictions.jsonl, outcomes.jsonl,
    logs.jsonl. Any bug can be replayed from its run folder.
  - Correlation id per user request, carried through ASR -> agent ->
    physics -> TTS -> UI.
  - Never log secrets. Mask keys. No personal data beyond what is needed.

11.4 FAIL LOUD, NEVER FAKE
  - Errors surface as errors or explicit incomplete states in the UI.
  - No placeholder "success" values. No silent fallbacks to canned data.
  - Fixture/test data is clearly labelled and never used in demo runs.

11.5 CONFIGURATION AND SECRETS
  - All tunables (thresholds, margins, prompts, ports, model ids) in
    config.py backed by .env. No magic numbers in code.
  - .env and runs/ are git-ignored. API keys never reach the phone app.

11.6 VERSION CONTROL
  - Private GitHub repo. Small commits. main always runs.
  - Tag working milestones (v0.1-core, v0.2-ui, ...). Tag the submitted
    version.

12. TESTING STRATEGY
==============================================================================
12.1 UNIT TESTS (pytest, no network, fast) - isolate the hard parts
  - SAM output parser: boxes/masks from saved raw text.
  - Row clustering and orientation detection: saved boxes for clean_front
    and clean_side -> expected 18 levels, correct orientations.
  - Slot classification: expected 54 PRESENT for the clean tower; a
    missing box WITHOUT positive gap evidence stays UNKNOWN (never
    EMPTY); a gap with background visible + crop re-check -> EMPTY.
  - Stability: per-block local-support check on offset/misaligned
    synthetic towers.
  - Geometry: contact rectangles, convex hull, signed distance.
  - Stability: the sanity cases in 6.4 plus edge cases (top level,
    bottom level, single remaining block, unknown slots).
  - VOI: unknown that does not matter -> answer; unknown that flips the
    verdict -> ask for the correct face.
  - Ledger: lock fingerprint is stable; locked records cannot be changed;
    outcome links to the right prediction.
  - Protocol: message encode/decode round trips.
12.2 FIXTURES
  - tests/fixtures/: clean photos + saved SAM raw outputs (replay without
    API cost), synthetic towers as JSON, recorded audio snippet.
12.3a SLOT-RECONSTRUCTION ACCURACY (M9)
  - Build >= 5 altered towers (blocks removed in known places, write the
    true layout down first). Scan with the normal flow.
  - Per slot, compare with truth. Report: correct, wrong, UNKNOWN.
    The critical metric is FALSE EMPTY (a present block reported empty)
    and FALSE PRESENT - both must be zero for the demo configurations.
12.3 INTEGRATION TESTS (opt-in: pytest -m integration)
  - Real SAM call on clean_front.jpg -> >= 34 detections.
  - Real Muse call on scene text -> valid structured reply, latency logged.
  - ASR on a recorded clip -> expected words.
12.4 PHYSICAL TRIALS (the real test) - TUNING SEPARATE FROM EVALUATION
  - Calibration set (>= 15): used to tune M_SAFE / M_FALL and fix bugs.
  - Freeze thresholds and code version (tag) before evaluation.
  - Evaluation set (>= 20): NEW configurations, frozen parameters.
  - Report for each set: number of trials, matches, mismatches,
    inconclusive predictions (separately), unclear outcomes, the setups
    and removal method, and every change made after tuning.
  - Any internal target (e.g., 80% agreement) is a working goal, not a
    safety claim; small samples do not give reliable accuracy estimates.
12.5 DEMO REHEARSAL CHECKLIST
  - Devices charged, glasses DAT session starts, Wi-Fi up, firewall port
    open, API keys valid, OBS scenes ready, spare built tower.
